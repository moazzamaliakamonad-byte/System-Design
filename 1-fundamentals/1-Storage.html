The Setup

Your App Needs to Remember Things

🧠 Analogy time. Think about how you remember things. Some things you keep in your head — fast, but limited. Some things you write in a structured notebook — organized, searchable. Some things you dump in a pile on your desk — flexible, chaotic, but findable if you know the keyword. Some things you mail to a storage unit across town — cheap, massive, but slow to retrieve.

Computers do the exact same thing. And picking the wrong storage for the job is how you end up with a system that works for 100 users and completely falls apart at 10,000.

Storage in system design is not just "use a database." It is about understanding the tradeoffs between speed, durability, consistency, cost, and structure — then picking the tool that fits your specific problem.

There is no universally best database. Anyone who says "just use PostgreSQL for everything" has never tried to store 500 TB of video files in PostgreSQL. Please do not try.

💬 Every startup, eventually
Day 1 architect, confidently:
"We'll just use MySQL. It'll be fine."
— 18 months and 50M users later —
"Why is our database the bottleneck for literally everything."

The good news: once you understand the types of storage and their core properties, you will have the vocabulary to make — and confidently defend — intelligent choices in any system design conversation.

Core Concept

The Big 5 Storage Types

Every database in the world falls into one of these categories. Click each tab to see how the same user profile is stored differently across paradigms — a great way to build an intuition for the tradeoffs.

Relational Databases (SQL)

Data lives in tables with predefined columns and types. Relationships between data are expressed through foreign keys and resolved with JOINs. The schema is rigid — defined upfront, enforced at every write.

Examples: PostgreSQL, MySQL, SQLite, Oracle, SQL Server, CockroachDB

Our user, stored relationally across two normalized tables:

user_idusernameemailcreated_atplan_id
1evanevan@example.com2024-01-152
2aishaaisha@example.com2024-02-031
3moazzamm@example.com2024-03-203

The plan_id is a foreign key pointing to a separate plans table. No plan data is duplicated — you JOIN to get it. Change a plan's name once and every user sees the update instantly.

💡
The power of SQL is in complex queries across multiple tables: "Give me all users who signed up in January, are on the Pro plan, made at least 3 purchases, and haven't logged in for 30 days." That's one SQL statement. Try doing that elegantly with a key-value store.
⚠️
The catch: Scaling relational databases horizontally (adding more machines) is genuinely hard. They were designed to scale vertically (bigger machine, more RAM). At extreme scale, this gets very expensive, very fast.

Document Databases (NoSQL)

Data is stored as self-contained documents — usually JSON or BSON. Each document can have a completely different structure. Schema is flexible — you don't define it upfront, and it can change per-document.

Examples: MongoDB, Firestore, CouchDB, Amazon DocumentDB, RavenDB

The same user, as a document:

{
  "_id": "user_a1b2c3d4",
  "username": "evan",
  "email": "evan@example.com",
  "plan": {
    "name": "Pro",
    "price": 29.99,
    "features": ["analytics", "api_access", "priority_support"]
  },
  "addresses": [
    { "type": "home", "city": "Lahore" },
    { "type": "work", "city": "Karachi" }
  ],
  "settings": { "theme": "dark", "notifications": true }
}

Notice: the plan is embedded directly inside the user document — no JOIN needed. Fast reads. The trade-off: if the Pro plan price changes, you might need to update millions of documents.

✓
Documents shine when: your data is naturally hierarchical, different items have different fields, you read/write entire records at once, and your schema is evolving rapidly.
⚠️
Watch out for: data duplication (denormalization), the lack of true cross-collection JOINs, and write amplification when shared nested data needs updating at scale.

Key-Value Stores

The simplest possible model: a giant distributed hash map. You give it a key, it gives you a value. No structure beyond that. No schema. No joins. No complex queries. Just pure, raw, blistering speed.

Examples: Redis, Memcached, DynamoDB (in KV mode), etcd, Amazon ElastiCache

The same user, decomposed into key-value pairs:

user:1:name→"evan"
user:1:email→"evan@example.com"
user:1:plan→"pro"
session:abc123xyz→"user:1"  (expires in 3600s)
ratelimit:api:user:1→42  (requests this minute)
leaderboard:global→Sorted Set {evan: 9420, aisha: 8870, ...}

A lookup is O(1). Redis handles millions of reads per second on a single machine. This is why it's used as a cache layer in front of every "real" database at scale.

✓
Perfect for: caching, session storage, rate limiting, leaderboards, real-time counters, pub/sub messaging, distributed locks. Anything where speed is the only thing that matters.
💡
Redis is in-memory by default — that's the source of its speed. It does support disk persistence (RDB snapshots + AOF log), but reboots can lose recent writes. Acceptable for a cache. Not acceptable for your bank ledger.

Wide-Column Stores

Imagine a relational table, but where each row can have a completely different set of columns. Rows are grouped by a partition key and distributed across nodes. Designed from the ground up for massive distributed write throughput and high availability.

Examples: Apache Cassandra, Google Bigtable, Apache HBase, ScyllaDB

The same users — notice how different rows can have different columns:

row_keyusernameemailpremium_sincelast_loginbeta_feature_x
user:1evanevan@ex.com2023-05-012024-03-15not set
user:2aishanot setnot set2024-03-10enabled
user:3moazzamm@ex.comnot set2024-03-18not set

Empty cells don't waste storage space — they literally don't exist on disk. In SQL, you'd need NULL columns for every row regardless. This makes wide-column stores very efficient for sparse data.

💡
Cassandra's superpower: it automatically partitions data across nodes using consistent hashing. Add 50 more nodes and it rebalances automatically. Netflix uses Cassandra for over 1 trillion requests per day for viewing history data.
⚠️
The tradeoff: you need to design your data model around your queries upfront. Ad-hoc queries and joins don't work. Your query patterns need to be known and stable. If they change, you may need to redesign your tables.

Graph Databases

Data is stored as nodes (entities) and edges (relationships between entities). Optimized for traversing connected data — queries that would require expensive recursive multi-level JOINs in SQL are trivial in a graph database.

Examples: Neo4j, Amazon Neptune, ArangoDB, TigerGraph, JanusGraph

🕸️
evan → [FOLLOWS] → aisha
aisha → [FOLLOWS] → moazzam
evan → [LIKED] → Post #42
Post #42 → [TAGGED_WITH] → Topic: System Design

The query "find friends-of-evan's-friends who also like System Design content" is a 3-hop traversal. In SQL: a nightmarish recursive JOIN. In Neo4j's Cypher language:

Cypher (Neo4j)
MATCH (u:User {name:"evan"})-[:FOLLOWS]->(:User)-[:FOLLOWS]->(fof:User)
WHERE (fof)-[:LIKED]->(:Topic {name:"System Design"})
  AND fof.name <> "evan"
RETURN fof.name, count(*) AS mutual_connections
ORDER BY mutual_connections DESC
✓
Use graph DBs for: social networks (LinkedIn, Twitter follower graphs), recommendation engines ("people who bought X also bought Y"), fraud detection (suspicious transaction patterns), knowledge graphs, and any domain where the relationships between data are as important as the data itself.

The Great Debate

ACID vs BASE

These are not database products — they are sets of guarantees about how a database behaves when things go wrong. And in distributed systems, things always go wrong. The question is how your database responds when they do.

⚗️ ACID

Guarantees correctness above all else. The gold standard for financial systems, inventory management, and anything where partial data is worse than no data.

A

Atomicity

All or nothing. A transaction with 5 steps either all succeed, or none of them do. If step 4 fails, steps 1-3 are automatically rolled back. Money cannot leave Alice's account without arriving in Bob's.

C

Consistency

The database always transitions from one valid state to another valid state. Business rules and constraints are always enforced. You cannot set a balance to a negative number if you have a constraint preventing it.

I

Isolation

Concurrent transactions cannot see each other's intermediate states. If two users simultaneously buy the last item in stock, only one transaction succeeds. The other sees the state after the first committed.

D

Durability

Once committed, it's permanent. Even if the server crashes, catches fire, or a junior dev runs DROP TABLE in prod — the committed data survives. It's written to non-volatile storage, typically with a write-ahead log.

🌊 BASE

Trades perfect consistency for massive availability and horizontal scale. The pragmatist's choice when you have more data than any single machine can handle.

B

Basically Available

The system guarantees availability (it responds to requests), but not necessarily with the most recent data. Even if 3 of your 10 nodes fail, the remaining 7 keep serving requests — possibly with stale data.

S

Soft State

The system's state may change over time, even without input — because replicas are asynchronously catching up to the latest writes. The state is not frozen; it's converging.

E

Eventually Consistent

Given enough time (usually milliseconds to a few seconds), all replicas will converge to the same value. A read right after a write might return stale data — but will eventually be correct. This window is the "inconsistency window."

🧭
The practical rule of thumb: Use ACID when correctness is non-negotiable — money, medical records, inventory, bookings. Use BASE when scale and availability matter more than perfect consistency — social media feeds, view counts, recommendation scores, search indices.

If your app shows a post with 10,002 likes when it actually has 10,000 — nobody dies. BASE territory. If your banking app shows $200 more than you actually have — that's a front-page news story. ACID territory.
😂 On eventual consistency, a classic exchange
PM: "Why does my tweet show 0 likes but my colleague's phone shows 47 likes on the same tweet?"
Engineer: "Don't worry. It'll eventually be consistent."
PM: "When exactly?"
Engineer: "...Eventually."
PM: *opens a Jira ticket titled "Likes broken"*

Going Deeper

Advanced Storage Concepts

These come up in virtually every senior system design interview. You don't need to memorize details — you need to understand the tradeoffs.

🗃️ Indexing — How reads become fast

+

Without an index, finding a specific row means scanning every row in the table — a full table scan. At 10 million rows, that's catastrophically slow. An index is a separate data structure (usually a B-Tree or Hash Map) that maps column values to row locations, enabling fast lookups.

📚
Library analogy: Without an index, finding a book about "Distributed Systems" means walking every single aisle. With an index (card catalog), you go directly to section 004.36.

B-Tree Index — The default in PostgreSQL and MySQL. Keeps data sorted, so it's great for both equality (WHERE id = 42) and range queries (WHERE age BETWEEN 20 AND 30). Lookup is O(log n).

Hash Index — O(1) exact lookup for equality only. Useless for range queries. Redis uses this internally.

Composite Index — An index on multiple columns: INDEX(last_name, first_name). The leftmost prefix rule applies: this helps queries on last_name alone, or last_name + first_name together, but NOT on first_name alone. Column order matters.

Covering Index — When an index contains all the columns a query needs, the DB can answer from the index alone without touching the main table. Zero disk I/O for the table data. Extremely fast.

⚠️
The write tax: Every index you add slows down INSERT, UPDATE, and DELETE operations because the index structure must be updated too. Index thoughtfully — only what your actual query patterns need.
🎯
Interview tip: When asked "how would you speed up this query?" — first verify there's an index on the WHERE clause columns. Then check if it's a covering index. That's 90% of the answer.

🔀 Sharding — Splitting data across machines

+

When your data outgrows one machine, you split it across multiple machines. Each machine (shard) holds a subset of the data. Together they hold all of it. This is called horizontal partitioning.

🍕
Pizza delivery analogy: You have 10,000 orders and one driver. Solution: hire 100 drivers, each covering their own neighborhood. Each driver is a shard. The dispatch system knows which driver handles which neighborhood (the shard key).

Sharding strategies:

  • Range-based: Users A-M → Shard 1, N-Z → Shard 2. Simple to implement, but causes hot spots if your data isn't evenly distributed. (Everyone named "Aaron" hits Shard 1.)
  • Hash-based: shard = hash(user_id) % num_shards. Evenly distributes data, but adding or removing shards requires rehashing and moving a lot of data.
  • Consistent hashing: A smarter hash approach that minimizes data movement when nodes are added/removed. Adding a node only reshuffles ~1/n of the data instead of everything. Used by Cassandra, DynamoDB, Redis Cluster, and most production systems.
  • Directory-based: A separate lookup service tracks where each shard's data lives. Flexible, but the lookup service becomes a potential bottleneck and single point of failure.
⚠️
Cross-shard JOINs are painful. If a User is on Shard 1 and their Orders are on Shard 3 (because they're sharded differently), joining them requires a network hop and cross-shard coordination. This is why sharding often forces denormalization — you embed related data in the same shard to avoid cross-shard queries.

📋 Replication — Surviving failures

+

Replication means keeping synchronized copies of your data on multiple machines. If one machine dies, the others keep serving. Reads can also be distributed across replicas, scaling read throughput linearly with replica count.

Leader-Follower (Primary-Replica) Replication:

  • One node is the leader — all writes go exclusively to it
  • Followers replicate the leader's write log asynchronously (or synchronously for stronger consistency)
  • Read-heavy systems distribute reads to followers — 3 replicas = 3x read throughput
  • If the leader dies, a follower is promoted via leader election (Raft or Paxos). This process takes seconds to minutes — during which writes may be unavailable

Multi-Leader (Active-Active) Replication:

  • Multiple nodes accept writes simultaneously
  • Ideal for geo-distributed systems — writes go to the nearest data center, minimizing latency for users worldwide
  • Hard problem: write conflicts. If Alice updates her profile on the US node and the EU node simultaneously, which update wins? Common strategies: last-write-wins, vector clocks, CRDTs, or application-level conflict resolution
💡
Replication lag is the delay between a write on the leader and when followers reflect it. During this window, a read from a stale follower returns outdated data. This is exactly what "eventual consistency" looks like in practice. The lag is usually milliseconds but can spike under load.
🎯
Read-your-own-writes consistency: A common technique is routing reads to the leader for a short window after a write, so a user always sees their own recent changes even if replicas are lagging. Used everywhere — you never see your own Tweet take 5 seconds to appear.

⚙️ CAP Theorem — The impossible triangle

+

CAP Theorem (proven by Eric Brewer in 2000) states that a distributed system can provide at most 2 out of 3 of these guarantees simultaneously:

  • Consistency (C): Every read receives the most recent write, or an error. All nodes see the same data at the same time.
  • Availability (A): Every request receives a response (not an error), even if it's stale data. The system never refuses to answer.
  • Partition Tolerance (P): The system continues to operate even when network partitions occur (i.e., some nodes cannot communicate with others).
⚠️
P is not optional. Network partitions happen in the real world — cables get cut, data centers lose connectivity. So the real choice is between CP (consistent but may reject requests during partitions) and AP (always available but may return stale data during partitions).

CP systems: PostgreSQL, MySQL, HBase, etcd, ZooKeeper — prefer to refuse requests over returning inconsistent data.

AP systems: Cassandra, DynamoDB, CouchDB — prefer to keep serving requests even at the cost of consistency. They let you tune the consistency level (eventual vs. strong) per query.

💡
Modern distributed databases like Google Spanner and CockroachDB push back on CAP by using globally synchronized clocks (TrueTime) to provide strong consistency at global scale — but at the cost of significantly higher latency and engineering complexity.

💾 Storage Hierarchy — Speed vs. Cost vs. Size

+

Not all storage is created equal. Understanding this hierarchy is why caching exists — it's one of the highest-leverage optimizations in all of engineering.

Bar length = relative speed (longer = faster). The speed difference between L1 cache and S3 is roughly 100 million times.

⚡
A cache hit at 100ns vs. a database disk read at 10ms is a 100,000x speedup. This is why caching is always one of the first scaling solutions in system design interviews — it's the highest ROI optimization that exists.

📦 Object Storage — For the big stuff

+

Databases store structured data. But what about videos, images, audio files, PDFs, ML model weights, binary blobs? That's what object storage is for.

Examples: Amazon S3, Google Cloud Storage, Azure Blob Storage, Cloudflare R2, MinIO (self-hosted)

Object storage uses a flat namespace (no real folders — just keys that look like paths) and is optimized for storing and serving large files reliably and cheaply. YouTube videos, Netflix movies, WhatsApp photos — all live in object storage.

🎯
The universal pattern: Store the file in S3. Store the URL or key in your database. When you need the file, fetch the URL from DB, then stream the file directly from S3 to the user. This is how literally every large application works. Never store binary files in your relational database — it's slow, expensive, and kills performance.

Object stores also provide lifecycle policies (automatically move files to cheaper tiers after 30 days), versioning (keep previous versions of a file), and CDN integration (serve files from edge nodes close to the user for low latency).

Show Me the Code

Code Examples

SQL — The right way to do a bank transfer

SQL (PostgreSQL)
-- WRONG: No transaction. If server crashes between these two lines, money vanishes.
UPDATE accounts SET balance = balance - 200 WHERE id = 1;
UPDATE accounts SET balance = balance + 200 WHERE id = 2;

-- CORRECT: Wrapped in an atomic transaction
BEGIN;

UPDATE accounts
SET balance = balance - 200
WHERE id = 1 AND balance >= 200; -- prevent overdraft at the query level

DO $$
BEGIN
IF NOT FOUND THEN
RAISE EXCEPTION 'Insufficient funds or account not found';
END IF;
END;
$$;

UPDATE accounts SET balance = balance + 200 WHERE id = 2;

COMMIT; -- Only now are both updates durable and visible to others
-- Any exception above causes an automatic ROLLBACK

Redis — Caching + Rate Limiting in Python

Python (redis-py)
import redis
import json
from functools import wraps

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

# Cache-Aside pattern: check cache first, fall back to database
def get_user(user_id: int) -> dict:
cache_key = f"user:{user_id}"

cached = r.get(cache_key)
if cached:
return json.loads(cached) # Cache HIT -- ~0.1ms

# Cache MISS -- hit the database (~5-50ms)
user = db.query(f"SELECT * FROM users WHERE id = {user_id}")
if user:
r.setex(cache_key, 300, json.dumps(user)) # TTL = 5 min
return user

# Rate limiting with sliding window counter
def is_rate_limited(user_id: int, limit: int = 100) -> bool:
key = f"ratelimit:{user_id}"
# INCR is atomic -- no race conditions possible
count = r.incr(key)
if count == 1:
r.expire(key, 60) # Start 60s window on first request
return count > limit

# Distributed lock (prevents concurrent writes to the same resource)
def acquire_lock(resource: str, ttl_seconds: int = 10) -> bool:
# SET NX = Set if Not eXists. Atomic. Returns True if lock acquired.
return r.set(f"lock:{resource}", "1", nx=True, ex=ttl_seconds)

MongoDB — Flexible document queries

JavaScript (Node.js / MongoDB)
// Find Pro users who logged in after Jan 1 and have 2+ addresses
const users = await db.collection('users').find({
'plan.name': 'Pro',
last_login: { $gte: new Date('2024-01-01') },
'addresses.1': { $exists: true } // index 1 exists = at least 2 elements
}).sort({ last_login: -1 }).limit(100).toArray();

// Upsert: update if exists, insert if not -- great for activity tracking
await db.collection('users').updateOne(
{ _id: userId },
{
$set: { last_seen: new Date(), status: 'active' },
$inc: { visit_count: 1 }, // atomic increment
$push: { activity_log: { ts: new Date(), action: 'page_view' } }
},
{ upsert: true }
);

// Aggregation pipeline: group users by plan and count revenue
const revenue = await db.collection('users').aggregate([
{ $match: { status: 'active' } },
{ $group: { _id: '$plan.name', total: { $sum: '$plan.price' }, count: { $sum: 1 } } },
{ $sort: { total: -1 } }
]).toArray();

From the Trenches

What Real Companies Actually Use

Because "I'd use a database" is not a system design answer. "I'd use PostgreSQL for user data with a Redis cache layer, S3 for media assets, and Cassandra for the activity feed" is.

🍽️ Netflix

Uses Cassandra for viewing history (1+ trillion requests/day — Cassandra was literally built for this). MySQL for billing (ACID required). S3 for video files. EVCache (their own Redis-based fleet) for caching user preferences and recommendations across all data centers. Elasticsearch for search.

🚘 Uber

PostgreSQL for trip data (ACID needed — money involved). Cassandra for location and driver history (extreme write throughput, BASE acceptable). Redis for real-time driver locations (millions of lat/lng updates per minute). Schemaless (their own MySQL-based document store) for flexible trip metadata.

💬 Discord

Started on MongoDB. Hit 100M messages/day and MongoDB couldn't scale writes. Migrated to Cassandra. Then migrated again to ScyllaDB (Cassandra-compatible, written in C++) — achieved 10x better performance at the same hardware cost. PostgreSQL for accounts and guilds. This is a perfect case study for "choose the right tool for the right scale."

📱 Twitter/X

MySQL for core tweet storage (with aggressive sharding). Redis for timeline caching — your home feed is pre-computed and stored in Redis as a sorted list (the "fan-out on write" approach). Hadoop + HDFS for analytics on billions of tweets. Manhattan (their own real-time distributed KV store) for high-throughput per-user data.

🔗 LinkedIn

Espresso (their own distributed document store built on MySQL) for member profiles. Voldemort (their own KV store) for high-throughput lookups. A graph database (custom-built) for the professional connections graph — computing 2nd and 3rd-degree connections for 900M users is a non-trivial graph traversal problem. Kafka as the central data pipeline between all systems.

Decision Guide

When to Use What

This is the framework interviewers want to hear when they ask "what database would you use and why?"

🗁️ Use Relational (PostgreSQL / MySQL) when...
  • Your data has clear, structured relationships
  • You need ACID transactions (payments, bookings, inventory)
  • You require complex queries with JOINs and aggregations
  • Your schema is stable and known upfront
  • You need strong consistency and data integrity
  • Team is familiar with SQL (very high leverage)
BankingE-commerceHealthcareERPs
📄 Use Document (MongoDB / Firestore) when...
  • Data is naturally hierarchical or nested
  • Different records have different fields
  • You read and write entire records at once
  • Schema will evolve rapidly during development
  • You don't need complex multi-collection joins
  • Your team thinks in JSON natively
CMSesUser ProfilesCatalogsEvent Logs
🔑 Use Key-Value (Redis / DynamoDB) when...
  • You need sub-millisecond response times
  • Access pattern is always "get by known key"
  • Data is ephemeral or derived (caches, sessions)
  • You need rate limiting, pub/sub, or leaderboards
  • Caching results in front of a slower database
  • You need distributed locks or atomic counters
CachingSessionsRate LimitsReal-time
📊 Use Wide-Column (Cassandra / Bigtable) when...
  • Extreme write throughput (millions of writes/sec)
  • Data is time-series or event-based
  • You need multi-region active-active availability
  • Query patterns are known and fixed upfront
  • Storing activity feeds, IoT telemetry, or logs at scale
  • Single-node SQL has hit its vertical scaling ceiling

In system design interviews: It's not only acceptable but expected to use multiple databases for different parts of the same system. PostgreSQL for user profiles. Redis for caching. S3 for files. Elasticsearch for search. Cassandra for activity feeds.

The key is to justify each choice with its tradeoffs: "I'd use Cassandra here because we need high write throughput and the query patterns are fixed, and I'm willing to trade ad-hoc queries for that scale." That's the answer that gets you hired.

Quiz Time 🧪

No pressure. But these exact questions show up in technical interviews. Prove it to yourself.

0 / 5
0 of 5 answered
1. A bank transfer deducts from Alice's account (step 1) then adds to Bob's account (step 2). The server crashes between steps. With proper ACID guarantees, what happens?
✓ Atomicity — "all or nothing." ACID guarantees that if any step in a transaction fails, the entire transaction is rolled back automatically to the state before it started. Alice keeps her $200. Nobody loses money. This is why transactions exist.
2. You're designing a social media platform where each post can have wildly different metadata: some posts have locations, some have polls, some have product tags, some have audio. Which database fits best?
✓ Document (MongoDB) — When records are heterogeneous (different structure per item) and data is naturally nested, document databases are the right fit. Relational would require dozens of nullable columns or a messy EAV pattern. MongoDB lets each document have only the fields it needs — clean, efficient, and flexible.
3. You add a B-Tree index on the email column to speed up login queries. What is the primary trade-off?
✓ Write operations slow down. Every index must be updated whenever data changes — on every INSERT, UPDATE, and DELETE. You're deliberately trading write performance for read performance. This is why you don't blindly index every column — only what your real query patterns actually need.
4. Your system uses Cassandra (an AP system per CAP theorem). During a network partition, a user writes a new profile picture. A read request comes in from a different region before the partition heals. What happens?
✓ Eventually consistent. Cassandra prioritizes Availability (A) over Consistency (C). During a partition, it keeps serving requests — but the read may return stale data. Once the partition heals and replication catches up, all nodes converge to the correct (new) profile picture. This is the BASE model in practice.
5. LinkedIn needs to show "People You May Know" — finding mutual connections between users in a graph of 900 million people. Which storage type is most appropriate for the connections data?
✓ Graph database. Multi-hop relationship traversal ("friends of friends who share your industry") is exactly what graph databases are optimized for. In PostgreSQL at 900M users, recursive JOINs would be catastrophically expensive. LinkedIn uses a custom-built graph store for precisely this reason. The right tool for the right job.
