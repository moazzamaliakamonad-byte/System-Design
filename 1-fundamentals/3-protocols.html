The Foundation

It's Just the Postal Service

📦 Analogy time. If you want to send a letter, you don't build the roads, drive the truck, or fly the plane. You just write the letter (Application), put it in an envelope (Transport), write the address on it (Network), and drop it in a mailbox.

The internet works exactly the same way through layered abstractions. Your web browser doesn't know how to encode electrical signals into a fiber optic cable, and the fiber optic cable doesn't care that you're sending a JSON payload of cat pictures.

We organize these layers using a conceptual framework called the OSI Model. While modern networking technically uses the simpler TCP/IP model, the OSI terminology is universally used in system design interviews and industry jargon.

Layer 4 Interactive Demo

Transport: TCP vs UDP

Once you have an IP address, how do you actually move the bits? You have two choices: a rigorous phone call (TCP) or firing a t-shirt cannon into a crowd (UDP).

📡 TCP EXPLAINING TO UDP
TCP: "Bro you can't just throw packets at the client without checking if they received the last one! What about packet loss? What about congestion control? What about ordering??"
UDP: "I ain't reading all that. Good for you tho. Or sorry that happened."

Connection-oriented and reliable. Before sending data, TCP performs a "3-way handshake" (SYN, SYN-ACK, ACK) to establish a connection. It guarantees that packets arrive in order, and if a packet drops, it will retransmit it.

✓
Use Cases: HTTP/HTTPS (web browsing), File Transfers (FTP), Email (SMTP), Text chat. Anywhere that missing a single piece of data ruins the entire payload.

Connectionless and fast. UDP just starts firing packets at the IP address. No handshake. No ordering guarantees. If a packet drops over the network, it is gone forever. It is lighter, faster, and has zero setup latency.

⚠️
Use Cases: Video streaming, Voice/VoIP calls, Multiplayer gaming. If you drop a frame of video in a live call, you don't want the network to pause and wait for it—you just want to render the *next* frame immediately.

Layer 7

Application Layer (APIs & Real-Time)

This is where software engineers live. Layer 7 is about how we format the data inside the TCP/UDP packets so the receiving application understands it.

1. DNS (Domain Name System)

Computers route traffic using IP addresses (e.g., 142.250.190.46). Humans use names (e.g., google.com). DNS is the distributed phonebook of the internet that translates names to IPs.

2. API Paradigms

REST (Representational State Transfer)

+

The standard of the web. Uses HTTP verbs (GET, POST, PUT, DELETE) on resource-based URLs (/users/123/orders). RESTful Semantics dictate that GET is idempotent (safe to retry), while POST creates new state.

GraphQL

+

Instead of hitting multiple REST endpoints, the client sends a single query describing exactly the shape of the data it wants. Fixes the "over-fetching" and "under-fetching" problems of REST, but makes caching much harder.

💀 FRONTEND DEVS BE LIKE
Frontend dev asking the REST API for just the user's avatar URL.
The API returning a 4.2MB JSON payload containing the user's avatar, entire purchase history, social security number, and zodiac sign.
"Chat, is this optimized?"

gRPC

+

Developed by Google. Instead of human-readable JSON, it uses Protocol Buffers (binary). Extremely fast, strongly typed, and uses HTTP/2 multiplexing natively. Highly favored for internal microservice-to-microservice communication.

3. Real-Time Communication

HTTP is strictly request-response. If you want a real-time chat app, polling the server every 1 second (GET /new-messages) is incredibly inefficient. We use two alternatives:

  • SSE (Server-Sent Events): A persistent, one-way HTTP connection. The client opens the connection, and the server pushes data down it (great for live sports scores or stock tickers).
  • WebSockets: A full-duplex, persistent TCP connection. Both the client and server can send messages to each other at any time asynchronously (essential for chat apps and multiplayer games).

Going Deeper

Request Lifecycle & Security

🔍 Request Lifecycle: What happens when you type google.com?

+

This is arguably the most common system design interview icebreaker. It demonstrates your understanding of the entire stack. Here is the exact sequence, down to the packets:

  1. DNS Resolution (UDP Port 53):
    The browser needs the IP address. It checks its local cache -> OS cache -> Router cache -> ISP DNS Resolver. If all fail, a recursive lookup occurs: Root Server -> .com TLD Server -> Google's Authoritative Server.
    Terminal
    $ dig +short google.com
142.250.190.46
  2. TCP Handshake (Layer 4):
    Before sending data, a reliable connection must be established. This takes 1.5 Round Trip Times (RTT).
    • Client sends SYN (Synchronize)
    • Server responds with SYN-ACK (Synchronize-Acknowledge)
    • Client responds with ACK (Acknowledge)
  3. TLS Handshake (HTTPS Security):
    The client and server negotiate encryption algorithms (Cipher Suites), exchange certificates, and establish a symmetric session key. This adds another 1 to 2 RTTs of latency before a single byte of HTTP data is sent.
  4. HTTP Request (Layer 7):
    The client finally sends the actual encrypted payload over the established connection.
    Raw HTTP Header
    GET / HTTP/1.1
Host: www.google.com
User-Agent: Mozilla/5.0
Accept: text/html
  5. Response & Render: The server replies with the HTML. The browser parses it, finds <link rel="stylesheet"> and <script> tags, and repeats this entire process for every static asset to render the final page.

🚪 Firewalls: Network ACLs vs Security Groups vs WAF

+

Not all firewalls are the same. Understanding where in the OSI model they operate is critical for debugging connectivity issues.

💀 THE STATELESS TRAP
Dev: *Opens port 443 INBOUND on the Subnet Network ACL*
Client: *Sends HTTPS request to server*
Server: *Tries to send the HTML response back on ephemeral port 34192*
The Network ACL blocking outbound traffic: 🛑✋
"Chat, why is my load balancer timing out?"
  • Security Groups (Layer 4, Stateful): Attached directly to a server (like an AWS EC2 instance). Because they are stateful, if you allow an incoming request on Port 443, the firewall automatically remembers the connection state and allows the outbound response, regardless of the port.
  • Network ACLs (Layer 4, Stateless): Attached to the entire subnet boundary. Because they are stateless, they do not remember active connections. If you allow Inbound Port 443, you must explicitly write a rule allowing Outbound Ephemeral Ports (1024-65535) so the server can actually reply to the client.
  • Web Application Firewall / WAF (Layer 7): Operates at the Application layer. It doesn't care about ports; it inspects the actual HTTP payload. A WAF can block a request because the JSON body contains a known SQL Injection signature (e.g., ' OR 1=1;--), even if the IP address and port are fully authorized.

Show Me the Code

Building a WebSocket Server

A simple Node.js implementation showing how a persistent, two-way WebSocket connection handles real-time chat, completely bypassing the standard HTTP Request/Response cycle.

JavaScript (Node.js)
const WebSocket = require('ws');

// Attach WebSocket server to port 8080
const wss = new WebSocket.Server({ port: 8080 });

wss.on('connection', function connection(ws) {
  console.log('New client connected!');

  // Listen for incoming messages from THIS specific client
  ws.on('message', function incoming(message) {
    console.log('received: %s', message);

    // Broadcast the message to ALL connected clients
    wss.clients.forEach(function each(client) {
      if (client !== ws && client.readyState === WebSocket.OPEN) {
        client.send(message);
      }
    });
  });

  // The server can push data to the client at any time
  ws.send('Welcome to the real-time chat!');
});

Industry Architecture

What Real Companies Use

🍽️ Netflix

Uses HTTPS (TCP) for the user interface, browsing, and fetching metadata (where reliability is required). However, the actual video streaming heavily utilizes adaptive bitrate streaming over HTTP, but historically and in specialized environments, media companies use UDP to prevent dropped frames from buffering the entire stream.

💬 Discord

Uses WebSockets for real-time text chat and presence (online/offline status). For voice and video calls, they use WebRTC which operates over UDP to ensure the lowest possible latency for gamers, accepting occasional audio glitches over delays.

🚘 Uber

Uses gRPC internally for hundreds of microservices to communicate with each other due to its binary efficiency and strict Protobuf contracts. The mobile apps communicate with the edge gateways using standard JSON over HTTPS.

1. You are building a live multiplayer First Person Shooter (FPS) game. Which transport protocol should you use for sending player movement coordinates?
✓ UDP. In an FPS, if a player's position packet from 50ms ago drops, you don't want the network to halt and re-request it (like TCP does). You just want the newest position packet instantly. UDP is fast and fire-and-forget.
2. Which API paradigm solves the "over-fetching" problem by allowing the client to specify exactly which fields it wants in the response?
✓ GraphQL. It was designed by Facebook specifically to prevent mobile apps from having to download massive REST payloads just to get a user's name and profile picture URL.
3. Which of the following networking security layers is STATELESS, requiring you to manually authorize outbound ephemeral ports?
✓ Network ACLs. Because they operate statelessly at the subnet boundary, they do not track active connections. Any outbound response must explicitly be allowed by an outbound rule.
4. Why might a company choose Server-Sent Events (SSE) over WebSockets for a live stock ticker dashboard?
✓ One-way data flow. A stock ticker only needs to push data down to the client. SSE is a simpler, native HTTP protocol built exactly for one-way server-push scenarios, whereas WebSockets require a persistent two-way TCP connection.
5. What is the very first step when a user types "github.com" into their browser?
✓ DNS Resolution. A browser cannot establish a TCP handshake until it knows the actual IP address of the server. It must query the Domain Name System first.
